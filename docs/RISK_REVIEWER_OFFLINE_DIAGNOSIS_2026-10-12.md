## 4. 警告实际上检测什么

`validate_references`（evidence.py:64–68）按每个 metric_values 键构造 `M-{metric}`，随后在以下任一条件下使用同一条“数值冲突”摘要：

1. 该 M-* ID 不在当前 claim 的 evidence_ids 中；
2. 查找到的 supporting_excerpt 不是 dict；
3. excerpt.value 与声明数值不相等（找不到指标也返回无 value）。

因此“数值冲突”并不专指算术矛盾；目录不存在、未引用及值不等未分别分类。也没有单位、时间、分组或分母字段可比较。该校验使用精确数值相等，不使用近似误差容忍；91.3 与91.333333… 会不相等，但历史是否这样声明未知。

本轮内存模拟验证：未定义 top3_spend、已知 spend 未引用、已知 spend 数值不同，均产生同类警告；正确值且正确引用没有警告。模拟是用来验证校验分支，不是重构历史输出或消除历史警告。

Schema 的 metric_values 允许任意字符串键，而计算目录仅有四项；Prompt 要求 computed 提供指标原值，却没有完整规定供应商计算、派生指标和别名的注册规则。这是已证实的契约表达缺口。不能据此删除告警或让未经验证的派生结论通过。

## 5. Reviewer 超时来源及调用链

`config.py:49` 读取 MODEL_TIMEOUT_SECONDS，默认45，范围1–120。该单一字段适用于**所有 Agent 的每一次请求**，不是 Reviewer 独有设置，也不是五阶段共用一个45秒倒计时。没有 RISK_REVIEWER_TIMEOUT 等独立变量。

同一个 config.timeout 同时用于：

- `config.py:74` 的 OpenAI-compatible SDK HTTP timeout；SDK max_retries=0。
- `engine.py:107` 的 `asyncio.wait_for(worker.run(...), timeout=config.timeout)`：整次 Agent.run 截止，包括模型请求等待、SDK响应处理和 Agent消息处理。

`engine.py:198` 另有 `asyncio.timeout(config.task_timeout)` 包围整个串行五阶段循环，总默认300秒。历史命令没有覆盖超时，报告记载45/300；当前只读加载同样得到45/300，进程未显式设置两项、项目无实际 .env。不能据当前状态重建当时所有环境变量，但报告与耗时相互支持。

历史 Reviewer 在45.01秒失败，HTTP观察器45.000秒结束且状态空；整个任务115.69秒，进入Reviewer前约70.68秒，还没有接近300秒任务时限。因此直接终止与**单次45秒截止**高度一致，而不是已用完任务总预算。

当前 MODEL_TIMEOUT 分类把 asyncio TimeoutError、SDK Timeout 类异常及总任务 TimeoutError 合并。没有保留确切异常类，因此不能唯一断定是外层 wait_for 先取消还是SDK超时先抛出。也不能将 HTTP 状态空写成网络不可达、认证失败、429或5xx。两层请求截止都为45秒，是准确到可用证据程度的结论；日志分类可进一步精细化但本轮未改。
