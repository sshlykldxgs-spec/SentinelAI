# 模型连接测试失败诊断

日期：2026-10-12（Asia/Shanghai）。本轮只读，未修改代码、配置、模型、密钥或Git，未调用真实API、未重跑Live。

## 1. 问题摘要

Final Release Verification 记录了一次真实连接测试：HTTP请求成功、收到模型响应，但UI的精确 `OK` 标记校验失败，因此没有进入Live工作流。本次失败不是HTTP、认证、模型不存在或finish_reason截断的已知失败。

## 2. 连接测试设计

当前实现位于 `backend/app/main.py` 的 `/api/model/test`：

1. 通过服务端当前进程内存配置创建 AutoGen `AssistantAgent`。
2. System message 是“只回复 OK”，task 是“连接测试”。
3. SDK重试显式设为0，输出上限设为64；请求成功后取Agent最后一条消息的 `content`。
4. 只有 `content.strip() == 'OK'` 且 `finish_reason != 'length'` 才返回成功。

这段逻辑同时承担两种用途：

- **用户连接验证**：用户点击“测试连接”时判断配置是否可运行。
- **近似自动化探针**：通过固定标记提供确定性断言。

两种用途的严格程度不同。固定标记适合内部自动化探针；对评委配置验证，HTTP成功且有正常文本响应更能回答“这个模型配置能否连接”。当前实现把它们混在一个入口，导致服务正常响应也可能被判定失败。

## 3. 实际失败响应证据

已有脱敏 HTTP 记录：

| 字段 | 值 |
| --- | --- |
| HTTP状态 | 200 |
| 实际返回模型 | deepseek-flash |
| finish_reason | stop |
| prompt tokens | 36 |
| completion tokens | 35 |
| total tokens | 71 |
| 请求耗时 | 0.731 秒 |
| API请求次数 | 1 |
| 自动重试 | 0 |

该记录说明服务正常返回并正常结束，排除了本次测试中的 HTTP 失败和 `length` 截断。原始响应正文没有持久保存，按安全要求没有恢复或打印，因此无法确认内容是：

- 完全返回了其它文本；
- `OK` 前后带有说明/标点；
- 模型输出了模型特有的 reasoning/格式内容，最后可见消息不是纯 `OK`；
- 或客户端最后消息文本与低层响应content存在转换差异。

只能确认严格字符串比较失败，不能把它写成模型或网络错误。当前UI显示的错误“接口返回了响应，但最小标记校验未通过”与证据一致。

## 4. 产品判断

### A. 保留严格 OK 标记

优点是断言确定，适合离线/内部自动化探针。缺点是容易把可用模型误判为失败，尤其不同模型可能附带礼貌词、推理字段或额外换行说明。当前行为属于此方案。

### B. 用户测试改为 HTTP成功 + 正常模型响应

优点是贴合评委任务：确认服务、凭据、模型和Chat Completions可工作。应同时要求 HTTP 2xx、非空文本消息、finish_reason 不是 length/content_filter，并显示返回模型；错误分类继续保留。缺点是“返回了响应”不等于模型完整兼容五阶段JSON Schema，不能替代Live任务验证。

### C. 分离用户测试与严格探针（推荐）

保留内部/离线严格标记探针；用户「测试连接」使用 B 的宽松连接判定，另显示说明“连接成功不代表五阶段结构化工作流已验收”。Live任务仍使用完整Schema校验、Reviewer和审批门禁。这样既保留自动化断言，也避免评委在正常连接上被 `OK` 文本细节阻断。

本轮不实施任何方案，按用户要求只诊断。若后续修改，推荐 C，修改范围仅限 `/api/model/test` 判定与脱敏响应消息，并新增分别覆盖严格探针/用户连接测试的离线测试；不改Agent、Prompt、Schema或Live执行链。

## 5. 已确认与未知

已确认：配置成功加载、请求发送、HTTP 200、模型字段可得、finish_reason=stop、没有自动重试、标记校验失败。

未知：原始模型文本、模型消息是否包含额外内容、AutoGen是否转换了reasoning字段、是否有服务商特有响应格式。由于原始正文未记录，不能离线恢复。没有在本轮追加真实请求。

## 6. 结论

当前失败更像是**用户连接测试的判定契约过严**，不是连接本身失败。建议未来采用 C：对用户连接入口宽松确认，对内部自动化保留严格标记；两者都不能冒充完整Live五阶段成功。到此停止。
